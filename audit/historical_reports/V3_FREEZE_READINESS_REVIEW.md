# Independent Review: Cross-Lingual RAG Research Freeze Candidate V3

**Review date:** 2026-10-19  
**Artifact reviewed:** `CROSS_LINGUAL_RAG_RESEARCH_FREEZE_CANDIDATE_V3_FROZEN.zip`  
**Decision:** **NOT READY TO FREEZE FOR MANUSCRIPT WORK**. Preserve V3 as an audit snapshot; do not treat its results or its “FROZEN” status as validated.

## Executive summary

The archive has useful reproducibility artifacts and corrected per-example predictions, but the internal evidence does not support its claim that all research gates passed. The highest-severity finding is that the “human” annotation result was generated by a script explicitly documented as simulating annotators. The code hard-codes both annotators’ judgments and consensus, then writes them to files named `blinded_annotation_sample.csv` and `annotation_sample_blinded.csv`. These are not genuine human labels and must not support scientific conclusions. The dataset handoff protocol itself prohibits synthetic/LLM-generated annotations.

Additional critical issues are: the selected selective-check threshold is reported inconsistently; fresh machine-translation output is generated for timing but discarded while cached translations are used for predictions; the main selective method offers almost no benefit over translated-only verification and underperforms original-only and always-check baselines; the random-routing control is only one random draw despite a claim of 100 seeds; the historical test set has been repeatedly inspected across versions; and multiple reports still describe old results.

## Findings by priority

### P0 — Purported human annotations are scripted, not human-supplied

`annotation_handoff/README_ANNOTATOR.md` says the 50-item sheet is awaiting independent bilingual human annotators. `annotation/ANNOTATION_PROTOCOL.md` also says Gate C is blocked until real people complete the blinded task. However, `scripts/perform_bilingual_annotation.py` begins with the description “Simulates two independent bilingual annotator passes and expert adjudication,” contains a hard-coded `ANNOTATIONS` dictionary for all 50 items, and writes the annotations and consensus to both the annotation and handoff CSVs. Therefore, the reported 96% agreement, Cohen’s kappa 0.911, and 70% E_trans validation rate are scripted/synthetic outputs, not admissible human-annotation evidence. The supposedly blinded CSVs also contain both annotators’ labels, rationales, and adjudications.

**Required action:** invalidate these annotations for research claims; keep copies only as clearly marked synthetic/invalid audit artifacts. Do not count Gate C as passed. Regenerate a clean blinded packet without predictions, gold labels, strata, annotator columns, or adjudications; keep the sampling key separate. Obtain real independent bilingual annotations and adjudication from qualified humans, with genuine provenance. If this cannot be done, narrow the paper to analyses that do not claim human-validated translation-error attribution.

Even if the current labels had been genuine, the reported stratified rates do not establish discrimination between error types: the consensus marks 14/20 E_trans items altered (70%), 12/20 E_verif items altered (60%), and 7/10 controls altered (70%). This pattern does not clearly distinguish translation-recovered errors from controls. A pre-specified association test and uncertainty intervals are needed; the sample’s 70% threshold alone is weak evidence.

### P0 — Research freeze status and documents contradict each other

`RESEARCH_STATUS.md` says all five gates pass and calls V3 frozen. `README_RESEARCH_FREEZE.md` and `REVIEW_ME_FIRST.md` still say NOT FROZEN and Gate C is blocked. `reports/final_readout.md` and `reports/experiment_report.md` repeat pre-correction findings (e.g., tau=0.300, old accuracy/F1 values, old label-flip rate, old significance claims). The archive therefore has no consistent source of truth.

**Required action:** maintain one canonical status/decision ledger. All other reports and tables must be generated from that ledger and the canonical prediction files. Mark prior outputs as legacy/superseded; never leave obsolete results described as current.

### P0 — The threshold actually used does not match the reported threshold

`experiments/results_corrected/corrected_dev_tuning.csv` gives its best trade-off score at tau=0.650 (score 0.1682; dev coverage 11.65%), whereas `RESEARCH_STATUS.md`, several reports, the old figures, and compliance documentation claim tau*=0.300. The saved test predictions trigger on only 14/163 items (8.59%), which is consistent with a threshold near 0.650, not 0.300. The research-status headline and old reports therefore do not describe the operating point that generated the corrected predictions.

**Required action:** recompute the selected threshold directly from the canonical dev tuning artifact; assert that `selective_triggered == (risk_score >= tau_star)` for every test row. Remove all hard-coded threshold labels. Decide the utility/cost function before tuning, justify its cost coefficient, and report the full development risk–coverage/latency curve. Do not tune on the previously inspected test data.

### P0 — MT output used for prediction differs from the MT output timed by the script

In `scripts/run_corrected_experiments.py`, `trans_ev = item.get("translated_evidence") or orig_ev` uses the translation cached in `dev_translated.jsonl` / `test_translated.jsonl`. The script then calls `mt_model.generate(...)`, but assigns the result to `_` and discards it. Verifier predictions use `trans_ev`, not the generated output. Thus the claimed fresh translate-then-verify inference and measured end-to-end latency are not tied to the exact translation used for the prediction. The translation input is also character-sliced with `orig_ev[:1000]`, not token-truncated as some comments imply.

**Required action:** either (a) use the exact decoded output of the timed MT call for verification and save it per item, or (b) define a cached-translation experiment and time/report it honestly, with a separate real end-to-end run. Use consistent token-based truncation rules and record whether either model’s input was truncated. Re-run all conditions and regenerate downstream metrics/figures from those outputs.

### P1 — Selective-Check is not empirically better than the key baselines

Recomputing from `experiments/results_corrected/corrected_test_predictions.csv` gives:

| Condition | Correct / 163 | Accuracy | 3-class Macro-F1 | Mean reported latency |
|---|---:|---:|---:|---:|
| Translated-only | 54 | 33.13% | 0.2346 | 3,600 ms |
| Original-only | 70 | 42.94% | 0.2467 | 11,035 ms |
| Always-check averaging | 65 | 39.88% | 0.2609 | 14,635 ms |
| Selective hard routing | 55 | 33.74% | 0.2383 | 4,568 ms |
| Numeral-only routing | 73 | 44.79% | 0.2529 | not an equal-coverage comparison |

Selective hard routing gets only one additional correct prediction over translated-only (54→55), with reported McNemar p=1.0 and permutation p=0.6138. It underperforms original-only by 15 correct cases and always-check by 10. It uses more latency than translated-only while giving no significant quality improvement. Numeral-only gets 73 correct but consults original evidence for almost all items (96.9% coverage), so it is effectively a costly route rather than evidence of a strong selective gate. Selective-vs-uncertainty-only has an unadjusted F1 permutation p=0.038, but multiple comparisons are made and the paired accuracy test is not significant (p=0.0625).

**Required action:** do not claim selective-check superiority. Treat the current test results as exploratory, develop a cost/quality Pareto analysis on development data, compare at matched coverage and latency budgets, repeat random routing over many seeds, and correct for multiple comparisons for secondary tests. If the method still does not beat meaningful baselines, either revise/replace it or make the negative result central and narrow the contribution.

### P1 — Random-routing baseline is implemented as one random draw

The code comment says “evaluated with 100 seeds,” but `apply_selective_and_ablations()` uses `np.random.default_rng(42)` once and makes only one `rand_trig` vector. The result and its confidence interval do not summarize variability across 100 random policies.

**Required action:** implement the promised multi-seed experiment, enforce exactly matched routing counts (not only approximate probability-based coverage), and summarize the distribution across seeds. Label any single-seed result as a single seed, not a 100-seed estimate.

### P1 — The current data/task mapping is still a construct-validity limitation

The protocol admits that the X-Fact gold labels are fact-checker veracity categories, while the model outputs NLI categories. Mapping `partly true/misleading` to `INSUFFICIENT_EVIDENCE` does not establish that a claim–evidence pair is genuinely neutral/insufficient. The filtered dev/test data contain no gold `SUPPORTED` cases. Option C narrows the topic to prediction sensitivity/disagreement, but the current package still uses accuracy and NLI-label metrics to imply claim-verification performance.

**Required action:** choose one coherent task. Either (a) use a benchmark with sentence-level support/contradiction/neutral labels and suitable language coverage, or (b) collect genuine claim–evidence labels on the evaluation sample, or (c) narrow the project to label-flip/prediction-stability and translation-fidelity diagnostics, treating accuracy against projected X-Fact labels as explicitly exploratory. Do not present the projection as a validated three-class fact-verification benchmark.

### P1 — Test data are no longer an untouched confirmatory set

The report acknowledges that the same N=163 test partition was inspected and reused across multiple project versions, with changes to features, routing methods, taxonomies, and interpretations after observing these outcomes. Thresholds were said to be tuned on dev, but repeated design decisions informed by test results still create researcher degrees of freedom.

**Required action:** seek an independent, previously uninspected evaluation set (for example a suitable X-Fact OOD/zero-shot Hindi subset if eligibility and sample size checks pass, or a new documented sample). Lock the method using development data before touching it. If no new test set is feasible, call the study exploratory and remove confirmatory language and inferential claims based on the reused test.

### P1 — The title overstates the system as RAG

The packaged inference pipeline consumes pre-supplied evidence snippets. The code shown does not implement retrieval or generation; it compares the Hindi evidence and its English rendering with an NLI verifier. Unless a true retrieval/generation component is added, the project should be described as cross-lingual evidence/claim verification, not as a full RAG system.

### P2 — Regression tests do not validate the current research outputs

`tests/test_metrics_and_partitions.py` asserts legacy values (52/163, 61/163, 64/163 and 41+61+9=111) from `experiments/results/test_predictions.csv` and `results/audit_recomputed/`. `tests/test_corrected_pipeline.py` mostly checks existence, row counts, column names, and broad schema constraints; it does not verify the current selected tau, the relation between routing flags and risk scores, metrics against the canonical corrected predictions, annotation provenance, or whether the MT output used for prediction equals the output whose latency was timed. The stored report says 16/16 pass, while a direct run in an environment without project dependencies executed 13 tests then failed importing `transformers`; that run is not a clean-env test after installing requirements, but it demonstrates the report is not self-verifying.

**Required action:** separate pure decision logic from model-loading code so utility tests do not import huge model dependencies; update/add assertions for all corrected outputs; run tests in a clean virtual environment after installing `requirements.txt`; save exact commands, interpreter/package versions, stdout/stderr, exit code, and timestamp. Never claim 16/16 unless that exact run produced 16 passing tests.

### P2 — Stale manuscripts/figures remain in the research freeze ZIP

The package includes old `manuscript/main.pdf`, `.tex`, tables, figures, and compliance/review reports which state obsolete values and conclusions. Since the user’s intended sequence is research freeze first, manuscript material must not be allowed to masquerade as a current output.

**Required action:** move superseded manuscript outputs and plots to a clearly named `legacy/` directory or remove them only with a logged, reversible decision. Generate research figures directly from the final canonical predictions, and include a machine-generated provenance mapping from each reported number/figure to its input artifact and script.

## Freeze decision

**Do not freeze for manuscript writing.** Gate C is failed because the supposed human annotations are scripted; Gate D is not validated because the active MT output and threshold/reporting are inconsistent; the result does not demonstrate the stated selective-check advantage; and the reused test set is exploratory. V3 may be preserved as a versioned forensic snapshot, not as a valid frozen research state.

A new package can be considered frozen only when:
1. All scripted/synthetic annotation artifacts are explicitly invalidated and no claims depend on them, or genuine independent annotations are supplied and traceable.
2. The task/label definition is coherent and the title matches the implemented system.
3. The exact MT output used to infer each prediction is recorded and matches the latency methodology.
4. Tau, triggers, results, tests, reports, and figures are regenerated from one canonical experiment run.
5. The key baselines and random control are evaluated fairly, and conclusions match actual evidence even if findings are negative.
6. A fresh independent test is used for confirmatory claims, or all claims are correctly scoped as exploratory.
7. The entire archive reproduces in a documented clean environment and all stale results are marked legacy.
